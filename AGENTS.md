# Repository Guidelines

`tgin` routes Telegram Bot API updates to downstream bot processes ("NGINX for Telegram bots"). One binary reads a YAML config (`version: 1`), ingests each bot's updates by long poll or webhook, routes every update by the bot's rules into named consumers, and serves them: **pull** consumers through a Telegram-shaped `getUpdates` endpoint, **push** consumers by POSTing to HTTP endpoints. The data plane also serves the Bot API itself to the downstream bots (the **gateway**): it proxies their calls to Telegram under per-bot rate limits and answers locally the calls that would disturb tgin. `README.md` and `DOCS.md` are the user documentation; `DOCS.md` is the reference for runtime behaviour (delivery semantics, the gateway, reload, admin API, metrics, shutdown, exit codes), and `docs/config-reference.md` is generated from the config model.

## Architecture & Data Flow

```
Telegram ─► source (long poll task, or webhook route on the data plane)
              │ extract facts once (update type, chat, user, text, command)
              ▼
           Engine::admit ─► RouteTable (rules, compiled) ─► reserve in every target queue ─► commit
                                                                   │
                         pull: LeaseQueue ◄─ getUpdates polls ─────┤
                         push: LeaseQueue ─► dispatcher ─► HTTP endpoints (retries, breakers)
```

1. **Sources** (`crates/tgin-botapi`): `LongPollSource` polls `getUpdates` and offers each update to a `Sink`, moving its offset past an update only once it is admitted; on backpressure it holds the batch. `webhook_router` serves one `POST <path>` per webhook bot, checks allowlist and secret on the head alone, and answers `503` + `Retry-After` on backpressure. `facts::extract` reads the routing facts from the raw JSON without building a `serde_json::Value`. `pull.rs` serves `getUpdates` from a pull consumer's queue (for `data_server.rs`'s routes and the gateway's `/c/<consumer>/bot<token>/getUpdates`); `gateway/intercept.rs` answers `getUpdates`, `getMe`, `setWebhook`, `deleteWebhook`, `getWebhookInfo`, `logOut` and `close` before the proxy, so none reaches Telegram as a downstream sent it.
2. **Engine** (`crates/tgin-core/src/engine.rs`, `admission.rs`): `Sink::admit` routes with the current `RouteTable` (swapped atomically on reload) and reserves room in every target (`backpressure` targets first, then `drop_oldest`), then commits; one queue lock at a time, nothing awaits. `Engine::set_runtime_endpoint` gives a push consumer with `accept_set_webhook` the endpoint its bot's `setWebhook` named (serialized with reloads, which clear it once that bot no longer feeds the consumer); a push consumer with no endpoint at all leases nothing.
3. **Consumers** (`crates/tgin-core/src/consumer/`): `PullConsumer::poll` acks by offset, returns held leases, else leases new updates and parks until the timeout; `PushConsumer` runs one dispatcher per consumer that leases up to `max_in_flight` and delivers with retries, per-endpoint breakers and balancing. With `webhook_reply: execute`, a delivery reads a method call from a 2xx answer (`crates/tgin-core/src/reply.rs`, at most 1 MiB) and awaits the `ReplyExecutor` before it acks the update; the executor is late-bound through `EngineRuntime.reply`, which the app sets to the gateway once it is built.
4. **App** (`crates/tgin/src`): `app.rs` assembles the engine, the gateway, the admin plane, the data plane and the sources, and runs the shutdown sequence; it also supervises `gateway-sweep`, which every 60 s drops the rate-limit keys back to a fresh key's state; `data_server.rs` serves webhook routes and `/c/{consumer}/getUpdates` plus aliases through an `ArcSwap<Router>` that reloads replace, with the Bot API gateway (`tgin_botapi::gateway::Gateway`) as every router's fallback; `admin/` is the admin plane (probes, `/metrics`, `/v1/*`) and `tgin admin`; `reload.rs` serializes reloads (SIGHUP, `POST /v1/reload`, file watcher) and bot moves (`POST /v1/bots/{name}/logout|close`: drain the server, park, drain tgin's queues, call `logOut` or `close`; waiting moves run before any reload not yet begun, on their own queue so a SIGHUP is never dropped) and applies reloads through `Engine::apply` (`crates/tgin-core/src/reload.rs`), then `Gateway::set_bots`, then the sources; `sources.rs` starts, stops and restarts bot sources, parks the bots moved off their server (in memory; only a reload that changes a bot's upstream starts it again) and records each `getMe` identity in the gateway.

### Bot API gateway

`tgin_botapi::gateway::Gateway` is every data-plane router's fallback (`data_server.rs::router`), so configured webhook paths, `/c/{consumer}/getUpdates` and aliases win. A request flows through `Gateway::handle` (`gateway/mod.rs`): `path::parse` (no gateway path → Telegram's JSON 404) → `Table::find` (`secret_eq` against every configured token, no early exit; unknown → 401) → `Engine::routes_to` for `/c/<consumer>/…` → GET/POST only → `intercept::Call::route` (the locally answered methods) → `proxy::forward`. The app builds the gateway after the engine and before the sources; `Gateway::set_bots` runs at start and on every reload after `Engine::apply`, and every `getMe` site in `sources.rs` calls `Gateway::set_identity`.

| File (`crates/tgin-botapi/src/gateway/`) | Role |
| --- | --- |
| `mod.rs` | `Gateway`, `GatewayBot`, the bot table (`ArcSwap<Table>`, swapped whole by `set_bots`; an entry keeps its client, identity and limiter while its token and settings stay), the parked bots (`set_parked`, apart from the table: `crates/tgin/src/reload.rs` parks a bot once its move's `logOut`/`close` succeeded, `Sources::unpark` and a bot's removal end it; a parked bot's calls that would reach a Bot API server or file origin, cloud and origin file routes included, get 503 `Retry-After: 5`, counted `rejected`; intercepts, pull `getUpdates` and disk files go on), disk-served files held in flight for the shutdown's drain (`Held`), `read_bounded` (the one bounded body reader). |
| `path.rs` | `GatewayPath::parse`: `[/c/<consumer>]/bot<token>/<method>` and `[/c/<consumer>]/file/bot<token>/<file_path>`, the token percent-decoded once and checked with `tgin_core::config::gateway_token` (the single token grammar). |
| `methods.rs` | The Bot API method table (`METHODS`, sorted by lowercased name; `lookup` ignores ASCII case) and `MethodSet` (`send*`-style patterns). |
| `intercept.rs` | `getUpdates` (scoped: `pull::poll` on the bot's pull consumer; bot path: 409), `getMe` (cached identity, else proxied and learned), `setWebhook`/`deleteWebhook` (runtime endpoint through `Engine::set_runtime_endpoint`, `drop_pending_updates` through `Engine::drop_pending`, both bound to the authenticating token), `getWebhookInfo`, `logOut`, `close`; descriptions and parameter order from telegram-bot-api's `Client.cpp`. |
| `files.rs` | The file route by upstream (`FileTarget`: the cloud's `/file/bot<token>/` proxied; a `files.url` origin proxied at `{files.url}/<token>/`, the path decoded once, checked and re-encoded; the bot's directory under `files.dir` served from disk; or 404 `files are not served for this upstream`) and the local-mode `getFile` rewrite (`Rewrite`, `rewrite_response`: a 2xx answer ≤ 64 KiB without `Content-Encoding` has the bot's own absolute path made relative; anything else passes verbatim). `bot_dir` tries `Upstream::token_dirs` (the token with its `:`, then with `~`; only `~` on Windows); `serve` streams a file with its length, `Last-Modified`, a weak `ETag`, conditional requests and single ranges, and answers 404 to any path whose canonical form leaves the bot's directory. Nothing here logs a path, a directory or a URL: they carry the token. |
| `proxy.rs` | The streaming proxy: header allowlists both ways, `Upload`/`Download` wrappers that keep `Content-Length` and stamp progress (`upstream_idle_timeout` = no progress in either direction while the request body is sent and while the response body streams; `Upload` also marks the body's end, after which the bot's response wait bounds the wait for the response headers: the upstream's `response_timeout`, or, on the `api_url` shorthand, `upstream_idle_timeout` as in v1, computed in `Bot::new`), `prepare` (buffers a covered method's JSON/form body ≤ 64 KiB and reads its chat) and `prepare_scanned` (the local file scan's bodies), `Call::admit` (the limits), `Call::send` (feeds `tgin_upstream_up`, except for the client's own failures and a file origin's), `flood` (the one resend after a 429), `Failed` (no HTTP answer, counted `unreachable` in `unreachable()`: the 502 says "unreachable" when the call was not executed: the server never had the whole request (the connect failed or never finished, an empty body included, or the upload stalled or broke off), or a 429 came whose body then broke (flood control refused the call); "the call may have been executed" after a lost connection or `response_timeout` once the whole request had gone; never resent; a `files.url` origin gets `upstream_idle_timeout` to answer and its own "the file server did not answer" / "the file server is unreachable"; `Failed::Idle` also covers a client stalling while tgin reads its body in `prepare`/`read_within`), `Tally` and `Call`'s drop guard (count each request exactly once; a request dropped before its outcome, because its client left, counts `client_closed`). |
| `limit.rs` | `BotLimiter`: the bot-wide quota is a `SlotCalendar` (the same GCRA as configured, kept as booked instants: a request takes the earliest instant at or after its start that keeps the set conformant, leaving earlier capacity free), per-chat and per-group are keyed GCRA quotas; all booked or none, each for the instant the request leaves (a quota booked for an earlier slot than the longest delay is cancelled and booked again from there); `sweep_limiters` for the app's `gateway-sweep` task. |
| `reply.rs` | The webhook-reply executor (`impl ReplyExecutor`, installed through `Gateway::reply_executor`, a `Weak<Gateway>` so the engine never keeps the gateway alive): Telegram's refusal rule plus the 64-byte `[A-Za-z0-9_]` method rule, the bot's limits, a runtime endpoint's reply only while `Engine::holds_token` confirms the token that set the endpoint (`Reply::bound_to`), the body posted verbatim once, bounded by the resolved upstream's `response_timeout` or 30 s, whichever is shorter (the `api_url` shorthand resolves to 60 s, so v1's 30 s stays); a parked bot's replies are refused, counted `refused`. |
| `local_files.rs`, `local_files/http_reader.rs` | Local file references for a bot on any `local` upstream (`local_mode` or not: the server may run `--local` whatever the config says) without `allow_local_files`: every parameter the server reads (query string, JSON at any depth and JSON carried in strings, urlencoded values, multipart text fields as telegram-bot-api's `HttpReader` parses them) is refused when, decoded, it begins with `file:`; `ScanGuard` scans a streaming body (multipart, or JSON and urlencoded over 64 KiB) frame by frame and fails it before the frame that completes a reference, passes 1 MiB of JSON or urlencoded text, or ends the body before the whole has scanned clean. Single-pass state machines, no recursion on JSON structure, total on any bytes. `http_reader.rs` is the port of TDLib's `HttpReader` (BSL-1.0, `LICENSES/BSL-1.0.txt`; its header names the td commit): header trimming, the boundary, the multipart grammar (the streaming `MultipartScan` and the in-memory `parts`) and urlencoded decoding. |
| `params.rs`, `chat_key.rs` | Request parameters (query, JSON top-level scalars, urlencoded, and multipart fields through `local_files`' port of the server's `HttpReader` grammar, the one grammar for multipart on the gateway path: the `setWebhook`/`deleteWebhook` intercepts and a webhook reply's `method` read a field as the server would) and the rate-limit chat key, which reads JSON and urlencoded bodies only; with `local_files.rs`'s scan, the only parameter readers on the gateway path. The fake (`tests/e2e/fake-telegram`) keeps multer, as it shares no code with tgin. |
| `errors.rs` | Telegram-shaped answers written by hand in Telegram's key order (serde_json would sort the keys). |
| `metrics.rs` | Every gateway metric family, registered once at start; per-bot handles, method handles resolved on first use and indexed by method. |

Rules on the gateway path: never log, trace or report a request path, an upstream URL, or a bot's directory or file path on a self-hosted server (all carry the token; log the bot and the method label); read a body whole only where one of these needs it, with its bound: covered send bodies ≤ 64 KiB (`proxy.rs`), JSON and urlencoded bodies scanned for local file references ≤ 64 KiB (`proxy.rs`, `local_files.rs`; longer ones stream through `ScanGuard`, refused past 1 MiB while they stream), Telegram's 429 bodies ≤ 64 KiB (`proxy.rs`), intercepted-method parameters ≤ 64 KiB and the `getMe` answer that fills the identity cache ≤ 64 KiB (`intercept.rs`), a local-mode `getFile` answer to rewrite ≤ 64 KiB (`files.rs`), Telegram's error answer to a failed webhook reply ≤ 64 KiB (`reply.rs`), and webhook replies ≤ 1 MiB. The gateway reads its bodies with `read_bounded`; webhook replies are read in tgin-core's push consumer (`PushConsumer::reply`, `MAX_REPLY_BYTES` in `crates/tgin-core/src/reply.rs`). Every answer tgin writes goes through `errors.rs`; compare methods ignoring ASCII case and label metrics with the table's canonical name. `crates/tgin/tests/gateway_bounded.rs` pins the constant memory of 200 MiB uploads and downloads, of a 200 MiB multipart upload scanned for local file references, and of 32 scanned 1 MiB JSON bodies in flight at once (about what as many unscanned ones take).

**Two client profiles.** Every outbound client comes from `tgin_runtime::http::client` (no redirects; environment proxies unless `no_proxy`). The **control profile** (`ClientOptions::default()`: 5 s connect, 10 s total) is the app's shared client: the sources' Bot API calls (a long poll extends its request's timeout to the poll's `timeout` plus a grace), `setWebhook` registration and push deliveries (each endpoint's `timeout` per request). `tgin admin` builds its own with `no_proxy` and its 60 s or 2 s bound. The **gateway profile** (one client per gateway bot: 5 s connect, `request_timeout: None`) has no total timeout, because a total timeout would cut slow uploads and downloads that are still moving; the proxy bounds idleness itself, and, once the request body has been sent, the wait for the response headers with the upstream's `response_timeout` (`upstream_idle_timeout` on the `api_url` shorthand; a local server may answer a large upload minutes later); webhook-reply calls set the smaller of the resolved upstream's `response_timeout` and 30 s per request (30 s on the shorthand, as in v1). Do not add a reqwest `read_timeout` to the gateway profile: in reqwest 0.13 it is one fixed timer until the response headers, so it would cut an upload that is still flowing.

**Maintaining the method table on a Bot API release.** Compare `METHODS` in `gateway/methods.rs` with the method list at <https://core.telegram.org/bots/api>: add and remove names keeping the order by ASCII-lowercased name, update the array length, the count in `method_table_sorted_unique`, the version in the table's doc comment and DOCS.md's "tgin knows the methods of Bot API …" sentence. Add new methods that send a message to `send_methods_present`, and check that the default `rate_limit.methods` (`crates/tgin-core/src/config/defaults.rs`, `send*`, `copyMessage*`, `forwardMessage*`) still covers them. A new method telegram-bot-api answers itself (its `Client.cpp` local methods), or one that would disturb tgin or another downstream, belongs in `intercept.rs`. A method missing from the table still works: it is forwarded with the metric label `other`, and only known methods are intercepted. The fake (`tests/e2e/fake-telegram/src/api.rs`) answers unknown methods 404; extend it when a scenario needs a new one. On a bump of the server image (`docker/telegram-bot-api/`), re-check `Client::get_input_file`'s local prefix (`file:/`) against `local_files.rs`'s `file:`, and diff, between the td commit named in `gateway/local_files/http_reader.rs`'s header and the td commit the new server pins, the TDLib functions the scan mirrors: those `http_reader.rs` ports (its header lists them), and `json_string_decode` (`tdutils/td/utils/JsonBuilder.cpp`) and `HttpReader::parse_json_parameters`, which `local_files.rs`'s `Values` and `unescape` mirror; update the code and the commit in both places together.

### Crate boundaries

Dependencies point one way: `tgin-runtime` ← `tgin-core` ← `tgin-botapi` ← `tgin` (and `xtask` → `tgin-core`; `tgin-fake-telegram` depends on no tgin crate, so the fake never shares code with what it tests). `tgin-runtime` knows nothing of Telegram or of the config model; `tgin-core` knows nothing of the Bot API's HTTP shapes (sources reach it only through the `Sink` trait and `Facts`); `tgin-botapi` does not know the app. Put code in the lowest crate whose concepts it needs; never add an upward dependency.

## Important Files

- `.github/workflows/ci.yml` — every check listed under [CI checklist](#ci-checklist).
- `.github/workflows/release.yml` — generated by dist (cargo-dist 0.32.0) from `dist-workspace.toml` (8 targets), with hand edits listed in its header. To regenerate, follow the steps in the `allow-dirty` comment in `dist-workspace.toml`, then re-apply the hand edits. Dry run: `dist plan --tag v1.0.0-dev` (the tag must match the package version). The release notes come from the matching `CHANGELOG.md` section; never write credential-shaped text there (e.g. `Bearer` followed by a word): the Actions runner masks it and drops any job output that contains it.
- `.github/workflows/image.yml` — on `v*` semver tags, builds amd64/arm64 images natively, publishes the multi-arch index to `ghcr.io/arynyklas/tgin` and attests it; `latest` goes only to the highest stable `vX.Y.Z`.
- `deny.toml` — cargo-deny: advisories, license allow-list, bans on `openssl`, `openssl-sys`, `native-tls`, `ring`; crates.io only.
- `crates/tgin-botapi/benches/` and `crates/tgin-botapi/tests/alloc_budget.rs` — hot-path benchmarks over the 1000 updates in `crates/tgin-botapi/tests/fixtures/updates.jsonl`, routed by `crates/tgin-botapi/tests/fixtures/hot_path.yaml` (shared setup in `crates/tgin-botapi/benches/common/mod.rs`). `hot_path.rs` is criterion (`cargo bench -p tgin-botapi -- --quick`). `hot_path_ir.rs` is gungraun under Callgrind (Linux, needs Valgrind and `gungraun-runner`), with a hard `Ir` limit per benchmark set to 1.5× the measured count. `alloc_budget.rs` is the allocation gate: the shared counting allocator (`crates/tgin-botapi/tests/support/counting_alloc.rs`, per-thread counter) asserting at most 2 allocations per update on the warm path, over `updates.jsonl` and over `updates_escaped.jsonl` (the same updates with every text, caption and callback data non-ASCII, `\u`-escaped as Telegram sends it). The gungraun limits are re-measured (Docker `rust:<version>` with `--security-opt seccomp=unconfined`) whenever the toolchain pinned in `bench-gate` changes: limits and toolchain move together.
- `DOCS.md`, `PERF.md`, `CHANGELOG.md`, `SECURITY.md` — user docs, benchmarks, release notes, security policy.

## Development Commands

```bash
# Build
cargo build --workspace                  # debug, every crate
cargo build --release -p tgin            # → target/release/tgin

# Run (reads ./tgin.yaml; or -c PATH / TGIN_CONFIG)
TOKEN=123456:ABC cargo run -p tgin
TOKEN=123456:ABC cargo run -p tgin -- config validate tgin.yaml
cargo run -p tgin -- admin status        # against a running tgin

# Tests
cargo test --workspace                   # every crate
cargo test -p tgin-core --test engine    # one integration test file
cargo test -p tgin-runtime queue::       # one module's unit tests

# Generated files
cargo xtask schema && cargo xtask config-docs

# Docker (mount the config's directory, readable by uid 65532; a single-file
# mount would never see an edit saved by rename)
docker build -t tgin .
docker run --rm -v "$PWD/config:/etc/tgin:ro" -e TOKEN=... -p 8080:8080 tgin

# Example stack
cd examples/simple && TOKEN=... TGIN_ADMIN_TOKEN=$(openssl rand -hex 32) docker compose up --build

# End-to-end suite (Docker; builds the images, runs the scenarios, tears down)
cargo xtask e2e            # --keep leaves the stack up

# Manual real-Telegram check before a release (a test bot's token; never in CI)
```

## Code Conventions & Patterns

### Hot path

The ingest path (getUpdates body → `split_updates` → `extract` → `Engine::admit` → queue commit) is gated by `alloc_budget.rs` (≤ 2 allocations per update on both fixtures) and, with queue commit, lease and ack, by `bench-gate` (instruction counts). Egress (`crates/tgin-botapi/src/pull.rs::batch_response`, push delivery) is not gated. Along these paths:

- **Payloads stay `Bytes`.** An update is its raw JSON from ingress to egress, never re-serialized; a pull response is assembled from the payloads as body chunks without copying (`crates/tgin-botapi/src/pull.rs::batch_response`). Facts are extracted once, borrowing from the payload, or for escaped text and callback data from a decode buffer the caller reuses (one per `getUpdates` batch). Ingress copies each `getUpdates` body and each single-frame webhook body once, to its exact size, so queued updates never keep hyper's read buffers alive; the updates of one `getUpdates` body share it.
- **Metrics handles are pre-resolved.** `CoreMetrics::source(name)` / `::consumer(name)` resolve every label combination once; the hot path increments handles and never hashes labels. A metric has one owner (e.g. only `Engine::admit` counts `tgin_routes_unmatched_total`).
- **No awaits and one lock at a time in admission.** Reserve, then commit; cancel reservations on refusal.
- **Rules are compiled.** `RouteTable::compile` does the work at load time; `route` writes into reusable scratch and does not allocate.
- **Swap, don't lock, for config-derived state.** The engine state, route table, data-plane router, running config and redactor sit in `ArcSwap`s that reloads replace.

### Secrets and redaction

- Secrets are `Secret<T>` (never shown by `Debug`/`Display`/serde); config URLs and paths are `Sensitive<T>`, used through `.expose()` and rendered masked (URLs as their origin only). Log through `tracing`, whose writer passes every line through the current `Redactor`; never print config text or URLs to stderr directly.
- Render `reqwest` errors with `tgin_runtime::http::describe_error` (no URL). Config errors never quote secret values or source lines.
- Every constant-time compare goes through `tgin_runtime::secret::secret_eq`.
- Outbound HTTP clients come from `tgin_runtime::http::client`, which never follows redirects; `tgin admin` asks it for `no_proxy`, so the admin token never passes a proxy.
- tgin never acts on its own pushes: every push carries `Via: 1.1 <pseudonym>` (`tgin_runtime::http::Via`, random per process), and both planes' routers are wrapped in `tgin_runtime::http::refuse_loops`, which answers `508 Loop Detected` to a request carrying it. The gateway's upstream requests and webhook replies carry it too (`Gateway::new` takes it), so an `api_url` pointing at tgin is refused, not recursed. Keep any new listener or router behind it, and any new outbound request to a configurable URL carrying it: with `accept_set_webhook`, a bot's token holder chooses push destinations.

### Config model

`crates/tgin-core/src/config/model.rs` keeps line and column for every error, so it uses no `#[serde(untagged)]`, no internally tagged enums and no `flatten` (they make serde-saphyr buffer and lose locations); string-or-object fields have hand-written visitors and schemas (`schema.rs`). Every field is either applied live by a reload or listed in `restart_required` (`crates/tgin-core/src/reload.rs`). Doc comments are the user-facing descriptions: they become the JSON Schema and `docs/config-reference.md`.

### Errors and tasks

- Errors are typed (`thiserror`); `expect` only for invariants. Exit codes live in `crates/tgin/src/exit.rs`.
- Long-running tasks run under `tgin_runtime::supervisor::Supervisor` (restart with backoff on `Exit::Retry` or panic, `Failed` on `Exit::Fatal`); graceful stops use `CancellationToken`s, never the supervisor's abort token.

### Unsafe

`unsafe_code` is denied workspace-wide. The only exception is the test-only counting allocator in `crates/tgin-botapi/tests/support/counting_alloc.rs` (`#![allow(unsafe_code)]`), which forwards to `System` with a `// SAFETY:` comment on each block; `crates/tgin-botapi/tests/alloc_budget.rs` and `crates/tgin/tests/gateway_bounded.rs` include it (the latter by `#[path]`), each with its own `#[global_allocator]` line. New unsafe code needs the same: a test-only or proven need, a scoped `allow`, and a `SAFETY` comment per block.

### Style

Imports follow the grouping of the file you edit; `cargo fmt` sorts within groups. Comments say why, not what.

## Testing & QA

- **Unit tests** are inline (`#[cfg(test)] mod tests`); **integration tests** live in each crate's `tests/`: `tgin-core/tests/{config,engine,push}.rs`, `tgin-botapi/tests/{longpoll,webhook,alloc_budget}.rs`, `tgin-runtime/tests/{http,watch}.rs`, `tgin/tests/{e2e,admin,panic_hook,gateway,gateway_bounded,gateway_files,gateway_intercept,webhook_reply}.rs` (`gateway_bounded` measures the whole process's heap, so it is a binary of its own, and its tests take turns through a shared lock; `gateway_files` covers the file modes, the `getFile` rewrite and the local file refusals).
- **Real boundaries.** HTTP peers are real servers (`wiremock`, or axum on `127.0.0.1:0`); config tests use `MapEnv` instead of mutating the process environment.
- **Paused clock.** Timer-driven logic (queue leases, supervisor backoff, engine drains, long-poll backoff) is tested on a paused clock (`#[tokio::test(start_paused = true)]` or `tokio::time::pause()`), so tests take no wall time and do not flake on slow machines; use real time only where real I/O has to make progress, with bounded waits. A paused clock jumps to the next timer whenever the runtime waits for a socket; where a test over real sockets asserts exact instants (the gateway's rate limits), `crates/tgin/tests/gateway.rs::freeze` holds that jump back with a blocking task, so time moves only by `tokio::time::advance`, and its bounded waits run on real time.
- **Child processes bind port 0.** `crates/tgin/tests/support/mod.rs::spawn_listening` starts the `tgin` binary with a config whose listeners use port 0 and reads the admin plane's bound address from the `admin plane listening` log line; it removes `RUST_LOG` from the child's environment (it would hide that info line). Never pick a port by binding and releasing it: another socket can take it before the child binds.
- **Signals.** Unix tests deliver real signals to a child process with `kill`; other app tests feed signals through `Signals::from_channel`.
- **Property tests** (`proptest`) cover the queue's invariants (`tgin-runtime/src/queue.rs`) and fact extraction against a `serde_json::Value` reference (`tgin-botapi/src/facts.rs`).
- **Performance / load tests** are not run by `cargo test`. They live under `tests/performance/` and require Docker, `make`, `curl` and `git` — see `tests/performance/makefile` and `benchmark.sh`. `ENGINE` selects the engine (`v1` default; `upstream` = the original engine, chesnokpeter/tgin at `UPSTREAM_REF` `4f0971a`, built with its own Dockerfile, its long-poll routes added through its management API; or both: `ENGINE="upstream v1"` alternates them run by run); `BOT_IMPL` selects the downstream (`rust` default = `tgin-bench bot`, 50 000+ updates/s; `py` = the aiogram bots, about 600–2 400/s per process depending on the engine and `max_in_flight`, which saturate before tgin does). A full pass over both engines is 6 scenarios × 3 RPS values (1 000, 5 000, 10 000) × 3 runs of 30 s plus container start-up, about 70 min; the generator is open loop and measures latency from each update's scheduled time. Results land in `tests/performance/results/<run_id>.csv` (13 columns, see PERF.md) next to `<run_id>.log` (per-run counters) and `<run_id>.stats.log` (`docker stats`). A run with `lag_p99_ms` above 0.5 measured the host, not the engine: `./rerun-invalid.sh results/<run_id>.csv` reruns those. Charts come from `tests/performance/diagram/main.py` (`uv run main.py [CSV ...]`); without arguments it plots the `results/*.csv` whose run id sorts last, and it deletes every PNG in `diagram/generated/` before rendering. Run the matrix on an otherwise idle machine (no cargo builds); PERF.md lists the machine, the upstream/v1 results and the harness's known limits.
- **End-to-end suite** (`cargo xtask e2e [--keep]`, `xtask/src/e2e.rs`; CI job `e2e` on Linux). It runs `tests/e2e/compose.yaml` (project `tgin-e2e`), waits for every service's health check, and checks eight scenarios through the fakes' call journals and tgin's `/metrics`: polling echo, restart confirm, files (a 100 000-byte document up and down), webhook delivery (captured and configured endpoints), webhook replies, the transparent 429 retry, per-chat shaping, and the self-hosted server (`fake-local`: files byte for byte through both bases from tgin's disk, the fake's own `/file` always 404 and tgin's metrics showing no upstream call for them; webhook ingress over plain http with an executed reply; `file:` references refused as JSON and as multipart, none reaching the fake). A final check confirms every exact count and that downstream `close`/`logOut` get tgin's 400 with nothing reaching either fake. Every check polls every 100 ms for at most 30 s (no fixed sleeps), and every exact count is checked again after the last scenario. On failure it prints the journal's tail and the compose logs; it always runs `docker compose down -v` unless `--keep`. The polling bots have fixed addresses in `10.231.77.0/24`, because tgin tells pollers apart by client address and the restart scenario needs a restarted bot to be the same poller. The fake tokens live in `compose.yaml` and in the runner (`e2e::tests::tokens_match_compose` keeps them in step). A new gateway behaviour that a framework exercises gets a scenario here; the fake follows telegram-bot-api (`Client.cpp`) wherever tgin depends on its behaviour.
- **Real-Telegram smoke** (`tests/smoke/real_telegram.py`), before a release and never in CI: it starts a built `tgin` (`--tgin`, default `target/debug/tgin`) with `real_telegram.yaml` against the real Bot API, a test bot's token from `TGIN_SMOKE_TOKEN` or a token file given as its argument. Phase A needs no chat; phase B prints instructions for a person to message the bot (`tgin-smoke-reply`) and checks long poll, pull, push, the webhook reply, shaping and a multipart round trip. It refuses to start when the bot has a webhook or pending updates, never prints the token, and scans tgin's log for it at the end. `--api-url` points it at another Bot API (the fake, for a dry run). `--self-hosted URL --files-dir DIR [--server-dir PATH] [--public-url URL]` runs both phases against a `telegram-bot-api --local` server (upstream `kind: local, local_mode: true`, files from disk) and adds the getFile rewrite, `file:` refusals, `tgin_bot_info`/`tgin_upstream_up`, a 53 MiB round trip and plain-http webhook ingress (a reload switches the bot to it for a second message, `tgin-smoke-hook`, and back); `--migrate` starts on the cloud and moves the bot with the real `tgin admin bot logout` after a typed confirmation, leaving it on the server; `--fake` injects phase B's messages through the fake's control API and checks its journal. tgin must see the server's directory under the server's names (`:` kept): on Windows, run it in a container on the server's network and files volume (Docker Desktop shows a bind-mounted `:` as U+F03A).
- Exercise the actual change before claiming it works: run the touched crate's tests, and for HTTP-facing changes a binary (`examples/simple`, the e2e suite, or `tgin` against the fake Bot API).

## Runtime / Tooling

- **Rust** edition 2024 in every crate, MSRV 1.89 (checked in CI), no toolchain pin. Tokio multi-threaded runtime with `runtime.worker_threads` workers (`auto` = one per CPU). Linux musl builds use mimalloc.
- **HTTP / TLS stack is fixed**: tokio, axum 0.8 + axum-server 0.8 (HTTP/1.1 only, rustls with ALPN `http/1.1`), reqwest 0.13 (`default-features = false`, rustls); one aws-lc-rs crypto provider. OpenSSL, native-tls and ring are banned in `deny.toml`.
- **Config**: YAML through serde-saphyr; JSON Schema through schemars.
- **Python and Node**: `examples/simple/`, `tests/e2e/bots/python/` and `tests/performance/diagram/` are `uv` projects with a committed `uv.lock`; `tests/e2e/bots/node/` is an npm project with a committed `package-lock.json` (`npm ci`); the perf bots (`tests/performance/bot/`) install `requirements.txt` with pip; `tests/smoke/` uses the Python standard library only.
- No package-manager wrappers and no root `Makefile`: work through `cargo` (the perf harness has its own `makefile`).
